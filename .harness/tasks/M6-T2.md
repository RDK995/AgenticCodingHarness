TASK  M6-T2 — the driver announces each milestone's start and finish exactly once, in order, through `start`

Tier: Mid (sonnet). Routing: reason_code ORDINARY_IMPLEMENTATION — wiring into the driver's step loop with ordering/exactly-once rules and updates to several existing end-to-end assertions; bounded to one production file, but "bounded" is less certain than a pure function.

Goal:
In `scripts/implement-loop.py`, the `Driver` sends a milestone-start notification (text from `milestone_start_summary`, added in M6-T1) and a milestone-finish notification (text from `milestone_finish_report`, added in M6-T1) through the existing `notify(self.project, self.config, text)` seam, so that across one driver run each milestone's start and finish are sent exactly once, in order, all before the final stop notification.

Relevant Requirements:
.harness/requirements.md FR8 ("Sent before the session that begins it, or, when the milestone was only planned inside that same session, as soon as the driver sees it has begun"), FR9 (finish report when a milestone reaches DONE), FR7 (every message names the project — `notify` already labels), Edge Cases ("Notification send fails ... the loop continues").

Acceptance Criteria:
- M6-AC1 For a fixture milestone, the start notification contains its id, name, goal/purpose, scope and acceptance criteria, taken from `milestones.md` / `state.json`, and is sent before the session that begins it (AC5, FR8).
- M6-AC2 When the milestone was only planned inside a session (no `milestones.md` before it), its start notification is sent as soon as the driver sees after that session that it has begun (FR8, Edge Cases).
- M6-AC3 When a milestone reaches DONE, the finish notification gives its id, name and result, the task count, the per-tier counts of task entry tiers (Cheap, Mid, Top) matching the fixture's `routing.tier` values, and the tier(s) of its review(s), in the shape "M3 DONE — 7 tasks: 4 Cheap, 2 Mid, 1 Top; reviewed by Top." (AC5, FR9).
- M6-AC4 A loop run through `start` with a fake session advancing a fixture over two milestones leaves, in the sink, each milestone's start and finish notification exactly once and in order, each naming the project (AC5, FR8, FR9).

Design (settled — implement exactly this):
- The Driver keeps two in-memory sets for this run: ids whose start was announced, ids whose finish was announced. (No persistence across separate `start`s; no state-schema change.)
- Before each step (in `run`, before `run_step` spawns the session): let `current = current_milestone(self.project)`. If `current` is not None and not yet start-announced, send its start summary and mark it.
- After each step (right after the after-snapshot is taken, BEFORE the outcome decides whether to break — so the last milestone's finish precedes the stop notification on "finished: every milestone is DONE"), walk state.json milestones in their recorded order. For each id: (a) if its status is anything other than `TODO` and it is not yet start-announced → send its start summary and mark it (this is the "planned inside the session and already begun" case, M6-AC2); then (b) if its status is `DONE` now, it was not `DONE` in the before-snapshot, and it is not yet finish-announced → send its finish report and mark it. Run this after every step regardless of the step's outcome.
- A milestone already DONE when the driver starts is never announced. A milestone that a session only planned (status `TODO`) is announced by the before-step rule of the next step that runs it.
- Building or sending an announcement must never stop the loop: wrap each announcement in try/except, log `could not announce <id>: <error>` to loop.log, and carry on. (`notify` already records send failures as "not sent".)
- Use the existing snapshot data (`take_snapshot` already records `statuses` in state order) rather than adding new state reads where it serves.

Test-helper changes (needed because notifications are now multi-line and more numerous):
- The file sink writes `<timestamp> <message>\n`; a start summary spans several lines. Change the test helper `notifications()` so it returns one entry per notification record: a line matching the existing `TIMESTAMP` regex starts a new record, and following lines that do not match are appended to it (joined with "\n"). Do not change the file sink.
- Every driver run now also sends a start notification for the fixture's current milestone. Existing assertions that a run produced exactly one notification mean "exactly one stop notification": update them to count stop notifications (records containing `implement loop stopped: `), keeping the exact-one check and every other check they make. A small helper such as `stop_notifications()` is fine. Refused-start tests (`loop did not start`) still produce exactly one notification in total — leave those as they are. Do not delete or loosen any other assertion.
