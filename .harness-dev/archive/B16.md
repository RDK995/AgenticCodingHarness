Behaviour under the tier pin is therefore proven, not reasoned. The orchestrator

**One process deviation, self-reported by the run:** the orchestrator's first
invocation returned early while its worker was still running, having produced
nothing; the driving session resumed it rather than re-spawning, so no duplicate
work occurred, but the milestone needed a second push. Recorded as an
observation, not a fixture failure — no expected outcome was affected. A single
run with no control cannot attribute this to the `sonnet` pin. See Follow-ups.

- **Pinning is the point, not just the value.** Before B16 the orchestrator and
  reviewer inherited the session model. That silently downgrades the reviewer on a
  cheap session — the exact failure `runtime-contract.md` warns about — and
  overpays for the orchestrator on an expensive one. A role's tier should be a
  recorded decision, not a side effect of how the session started.
- **Archive split is a move, never a summary.** Completed evidence is the record of
  what was actually verified; summarising it would destroy the thing the repository
  exists to protect. Proven by reconstruction against git rather than asserted.
- **Runtime archiving is threshold-gated at ~400 lines.** Unconditional archiving
  would break `fixtures/05-golden-path`, which requires a completed single-milestone
  `milestones.md` to carry every template heading in order. Short projects archive
  nothing.
- **No token accounting, budgets, or configuration added.** V1 excludes workflow
  infrastructure. The changes are instructions, state layout, and three frontmatter
  lines.
- **`.claude/RESUME.md` left alone.** It is a Claude Code checkpoint artifact under
  a gitignored directory, not harness state.

### Follow-ups

- **Orchestrator early return, observed once.** During the fixture run the
  orchestrator's first invocation returned having produced nothing while its
  worker was still running. Recovered by resuming rather than re-spawning, so no
  duplicate work — but it cost a second push. Watch for a recurrence across the
  next few runs. If it repeats, the substitution point is one frontmatter line in
  `agents/orchestrator.md` back to `opus`, documented in `runtime-contract.md`.
  One run with no control is not enough to attribute it to the `sonnet` pin.

- **The runtime `implement` skill has no session boundary.** §39's first solution
  item — a completed milestone ends the session — was applied to `CLAUDE.md` (this
  repository's own build) and to `agents/orchestrator.md`, but
  `skills/implement/SKILL.md:31-56` still loops every milestone in one driving
  session. Partly self-mitigating: each milestone runs inside an orchestrator
  subagent, so the driving session accumulates returns rather than the work — the
  opposite of the zero-delegation pattern that produced the measured 84%. **Not
  carried into B17** (B17 is tier work); still open as §39 residue.

- **Ranged reads are dev-side only.** `grep -rln "sed -n" agents skills docs`
  returns nothing; §39 item 4 was applied to `CLAUDE.md` alone. Low impact while
  user requirement documents stay small.

- **The final review reads the whole archive.** `skills/implement/SKILL.md:75`
  hands the reviewer every archived milestone file, at the `opus` tier, when the
  archive is at its largest — archiving's saving is given back on that one call.
  Likely correct (a holistic review needs the whole picture) but it is the peak
  cost, and worth knowing before anyone tries to trim it.
- The measured 84%-of-spend-above-100k figure came from reading this project's own
  session transcripts. Worth re-measuring after a few milestones under the new
  protocol to confirm the boundary rule is actually being followed, rather than
  assuming it is.
- `docs/implementation-plan.md` is 1705 lines and every session reads part of it.
  If section-scoped reads prove insufficient, splitting it per phase is the same
  move applied one level up. Not done now: no evidence yet that it is needed.
