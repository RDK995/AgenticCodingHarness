TASK  M1-T2 — detached driver: start / status / stop lifecycle
Tier: Top (opus) — reason_code DIFFICULT_CONCURRENCY: detached process sessions, signal handling across driver/step/caffeinate, and pid liveness races.

Goal:
Create `scripts/implement-loop.py`, a Python 3 stdlib-only CLI whose `start` launches a detached background driver, `status` reports it, and `stop` ends it cleanly — the walking skeleton of the unattended loop. The step it runs is a placeholder that later milestones replace; build the seams, not the later behaviour.

Relevant Requirements:
.harness/requirements.md FR2, FR3, FR13 (lines 20-28, 81-84), AC2 (90-94), Edge Cases "stop while no driver", "stale pid file", "stop mid-session" (156-160). Milestone: .harness/milestones.md "M1" section (Outcome + M1-AC2, M1-AC3, M1-AC4).

Acceptance Criteria (this task):
- M1-AC2: with a fake `claude` binary and a file notification sink, `python3 scripts/implement-loop.py start` returns promptly (well under 5 s) while a detached driver — in its own session (os.getsid(driver) != os.getsid(invoker); started with start_new_session=True; stdin/stdout/stderr detached) and NOT a child of the invoking process — runs `caffeinate -w <driver pid>` and writes `.harness/loop/driver.pid` and `.harness/loop/current-step.json`. `status` prints running, the pid, the current step number and the milestone being worked on, exit 0.
- M1-AC3: `stop` terminates the running step (SIGTERM to the step's process group, then SIGKILL after the grace period if still alive) and the driver, removes driver.pid, leaves `.harness/loop/loop.log` and the project's git history/working tree untouched, and produces exactly one stop notification in the sink. `stop` waits for the driver to exit (bounded) before returning, prints that it stopped, exit 0.
- M1-AC4: `stop` and `status` with no pid file, or with a pid file naming a process that is gone, print "not running" and exit 0 (a stale pid file may be removed).

Interface (fixed — later milestones and the skill depend on it):
  python3 scripts/implement-loop.py start  [--project DIR] [--claude PATH] [--notify-file PATH] [--grace SECONDS]
  python3 scripts/implement-loop.py status [--project DIR]
  python3 scripts/implement-loop.py stop   [--project DIR]
- --project defaults to the current directory. State dir is <project>/.harness/loop/ (create it).
- --claude defaults to env HARNESS_LOOP_CLAUDE, else "claude" resolved on PATH.
- --grace defaults to 20 seconds (float allowed so tests can use e.g. 1). Persist it so `stop`/the driver use the start-time value.
- Notification seam: a small sink abstraction (e.g. a `notify(message)` function chosen from config) with a FILE sink that appends one line/record per notification to --notify-file. With no sink configured, a notification is not sent and is recorded in loop.log as "not sent: no sink configured" (ntfy arrives in M5 behind the same seam). Exactly-one stop notification must be guarded (a flag), whatever path ends the driver.
- caffeinate binary: "caffeinate", overridable by env HARNESS_LOOP_CAFFEINATE. It is started by the driver with `-w <driver's own pid>`.
- current-step.json: {"step": <int, 1-based>, "milestone": <id or null>, "attempt": <int>, "pid": <step pid>, "started": <ISO time>}. The milestone is the first milestone in <project>/.harness/state.json (object key order under "milestones") whose "status" != "DONE"; null if no state.json.
- The step (placeholder for M2): run `[claude, "-p", "/harness:implement"]` with cwd=project, start_new_session=True, stdout/stderr to a file under .harness/loop/ (e.g. step-<n>.out). Put the decision about what happens after a step in one function (e.g. `judge_step(...)`) — in M1 it returns a "finished one step" outcome and the driver then ends: writes `.harness/loop/outcome.json` ({"outcome": ..., "time": ..., "milestone": ...}), sends exactly one stop notification, removes driver.pid, exits. Do not implement FR4 checks, FR6 conditions, permission flags, environment filtering, or ntfy — later milestones own those.
- Stop path: `stop` sends SIGTERM to the driver; the driver's handler terminates the step group (SIGTERM, wait grace, SIGKILL), stops caffeinate, writes outcome.json with outcome "stopped by owner", sends the one stop notification, removes driver.pid, exits.
- pid liveness: os.kill(pid, 0) plus a check that the process is this driver (e.g. `ps -o command= -p <pid>` contains "implement-loop"), so a recycled pid reads as stale.
- loop.log: append human-readable timestamped lines at least for: driver started, step started (step, milestone, attempt), child processes started (pid + command line), step ended, notifications (sent / not sent + reason), final outcome. (A later task refines the exact log content; just keep logging in one helper.)

Tests — new file .harness-dev/test-implement-loop.py (stdlib unittest, style of .harness-dev/test-guard-bash.py; ROOT = Path(__file__).resolve().parents[1]). Each test uses a temp project dir (git init, one commit, a fixture .harness/state.json with milestones M1 DONE and M2 IN_PROGRESS) and a fake `claude` shell/python script written into the temp dir. Write the tests first and see them fail (Red). Cover at least:
  1. start returns < 5 s; driver.pid appears; driver pid != child of test process and getsid differs from the test's; a `caffeinate -w <driver pid>` process exists (check via `ps -axo pid,ppid,command`); status prints "running", the pid, step 1 and "M2".
  2. stop with a fake claude that sleeps: step and driver gone, driver.pid removed, loop.log still present, git log/HEAD unchanged, notify file has exactly one line.
  3. stop with a fake claude that traps/ignores SIGTERM and --grace 1: it is SIGKILLed; driver exits; exactly one notification.
  4. status and stop with no pid file, and with a pid file containing a dead pid: print "not running", exit 0.
  5. a fake claude that exits immediately: driver ends by itself, outcome.json written, exactly one notification, driver.pid removed.
  Always clean up any process a test started (tearDown kills by pid).
