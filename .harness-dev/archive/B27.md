### Design decisions

- **The agent is `as-built`, not `architect`.** The human asked for "the
  architect" and the architect *skill* keeps the design job — deciding and
  agreeing the intended architecture. Recording what was built is a different
  job with a different tier and a different safety argument, and B25 already
  made exactly this call when it gave the verifier its own definition rather
  than pointing the reviewer at a task. A skill and an agent sharing one name
  and doing opposite things is the confusion that decision avoided.
- **It records; it does not judge.** No verdict, no severity, no suggested
  correction. This is what makes the Cheap pin defensible, on the same argument
  §48 used for the verifier: an agent that concludes nothing cannot conclude
  wrongly. The reviewer grades what it recorded.
- **Its output never enters the orchestrator's context.** The agent writes the
  file; the milestone record carries a path and a one-line result. §48 measured
  52 of 58 orchestrator `Read`s going to subagent output files — a diagram is
  the same mistake in a different shape, and it would be re-paid on every
  following turn.
- **The comparison unions the milestone records rather than re-deriving from the
  finished tree.** Chosen by the human from the two options. It is free, and it
  carries attribution — it says which milestone moved a boundary, not only that
  one moved. The cost is that it inherits a milestone's error, which is why
  COMPOSE reports disagreements between milestones instead of merging them.
- **The comparison is a report, not a gate.** Undeclared divergence is
  `IMPORTANT`, exactly as §36 already grades drift; a divergence reconciled to a
  `D<n>` is not a finding. No completion criterion changed.

### Cost

One Cheap context per milestone plus one at the end. At the measured Cheap rate
(~285k) a ten-milestone project adds roughly 3M tokens — about 1.3% of the 221.8M
§48 measured for a single milestone of `openCodeOpenWeightHarness`. That figure
holds only while the context boundary does: a diagram read into the orchestrator
stops costing 285k once and starts costing its own size every turn.

### Validation — task 6, the three criteria the fixtures could not reach

All three are now proven. `7 / 7 acceptance criteria proven`, from three runs.

**Run A — the architect writes a conforming `## Diagram`.** Two live
`harness:architect` runs against scratch requirements, single-shot with
pre-agreement so the run reaches `AGREED` in one turn.

The first produced a **one-component** architecture for a one-function CLI, and
its diagram is a single node with no edges. That is the right answer and a
better test than a graph would have been: the rule is that the diagram *renders*
`## Components` and `## Interfaces`, so an architecture with no boundary must
produce a diagram with no edge. Inventing one to look like a diagram is the
failure.

The second was given a requirement forcing a seam (a testability constraint
requiring the formula be callable in isolation) and produced two components, one
edge, `C2 -->|"celsius_to_fahrenheit(celsius: float) -> float"| C1`. Checked
against the text: both nodes appear in `## Components`; the single edge matches
C2's `Depends on: C1`; the edge label is the `## Interfaces` entry verbatim.
Nothing in the diagram is absent from the text and nothing in the text is
missing from the diagram.

A third instance ran on a real project (see the DartsApp note below) and
produced seven components and eight edges, conforming on the same check. That
one matters more than either fixture: it is the first architecture this skill
has drawn at a size where a reader genuinely cannot hold the graph in their
head from prose, which is the case §50 was written for.

### Follow-ups

- **CLOSED — the subtlest divergence was drawn but not characterised.**
  `search.py` re-implements `read_all()` by parsing the notes file itself,
  contradicting C2's stated ownership. Both earlier runs drew the edge and cited
  it; neither said the ownership claim was contradicted, and the open question
  was whether the reviewer could reach that from the edge alone. Run C says yes,
  and did it by demonstration rather than assertion — see Validation. The
  division of labour holds: the Cheap context draws the edge, the reviewer
  decides what it means.
- **CLOSED — task 6 needs a golden-path fixture with an architecture.** That is
  `13-architecture-golden-path`.
- **OPEN, and a contradiction rather than a gap: a passing final review records
  nothing.** Fixture `13`'s final review returned `PASS` and wrote nothing to
  `milestones.md`. That is correct per the current contract —
  `milestones-template.md` says `## Final Review` "exists only once every
  milestone is `DONE` **and the final review returned findings**", and
  `SKILL.md`'s `PASS` branch only says "tell the user implementation is
  COMPLETE". But `fixtures/05-golden-path/EXPECTED.md` requires the opposite:
  "recorded under a `## Final Review` heading" for a review reporting
  `COMPLETE`. Both cannot be right, and `05` has been passing while carrying an
  expectation the contract contradicts.

  Not resolved here, because resolving it changes the skill and B27 is not the
  milestone for that. Recorded with a view: the final review is the most
  expensive single invocation the harness makes, and on the current contract its
  verdict and its tier survive only in the chat transcript. A fresh session
  reading `milestones.md` cannot tell whether the project was ever finally
  reviewed. That is precisely the state the "conversation is not the
  authoritative source" rule exists to prevent, so the template is the likelier
  side to be wrong.

- **The as-built path has still never run on a multi-milestone project.** Both
  `10` (two milestones, hand-written records) and `13` (one milestone, real
  records) stop short of the case COMPOSE was actually built for: a
  responsibility migrating one step per milestone across four or five of them,
  which is §50's stated motivation and which no per-milestone check can catch.
  `13` proves the wiring; it does not prove the wiring earns its cost. The first
  real project to reach all-`DONE` with an architecture is the evidence, and
  DartsApp may become it.
