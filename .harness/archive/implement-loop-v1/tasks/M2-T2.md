Goal:
Turn the M1 driver (one step, then end) into a loop: run a fresh step session, then judge the step from `.harness/state.json` / `.harness/milestones.md` as they are on disk after the session, and either start the next fresh session or stop. Each step is a NEW process built by the existing step-session builder (from M2-T1) with the prompt `/harness:implement`, in the project directory.

Relevant Requirements:
.harness/requirements.md FR5, FR6(a) (lines 34-48), Edge Cases (lines 143-162). Milestone .harness/milestones.md M2 (Outcome, M2-AC1, M2-AC2).

Acceptance Criteria:
- M2-AC1: Driven through `start` by a fake implement session that advances a fixture `.harness/state.json`, the driver runs successive fresh `claude` processes, one per step, in the project directory, each invoking `/harness:implement`, and decides each step's result from `state.json` / `milestones.md` rather than from the session's output alone.
- M2-AC2: A session ending at a normal phase boundary (for example a milestone left at REVIEW) with state progress counts as progress and the next fresh session starts; when every milestone is DONE the loop stops as finished.

Decisions already taken (do not re-decide):
- Snapshot before each step: the parsed `state.json` (milestone id -> status, plus `current_milestone`) and the raw bytes/hash of `milestones.md` (absent counts as a value). After the step, compare.
- Judge result (replace `judge_step`, keep it a pure function of (before snapshot, after snapshot, returncode, stopped) so it is unit-testable):
  - stopped by owner -> outcome "stopped by owner" (existing behaviour).
  - after-state exists, has at least one milestone, and every milestone status is DONE -> stop, outcome "finished: every milestone is DONE".
  - state changed (any milestone status changed, a milestone added/removed, `current_milestone` changed, or milestones.md content changed) -> "progress"; log it and start the next fresh step (step number +1, attempt 1).
  - otherwise (no state change) -> a failed step. INTERIM for M2 only: a failed step stops the loop with outcome "failed step: no state progress". (M4 will replace this with "two consecutive failed steps"; do not implement the consecutive counter or any other FR6 stop.) Log "step N outcome: failed step: ..." in loop.log.
  - A session's exit code alone never decides progress: a session that exits 0 with no state change is a failed step; a session that exits non-zero but advanced state is progress.
- Write `current-step.json` per step as today (step number increases each step). Keep the per-step output file `step-<n>.out`.
- Keep the existing "step N started: milestone X, attempt A" and "step N outcome: <outcome>" loop.log lines for every step.
- Existing test `test_driver_ends_by_itself_after_one_step` asserts outcome "finished one step"; its fake makes no state change, so under the new rule its outcome is "failed step: no state progress".
