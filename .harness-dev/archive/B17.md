### Validation — `fixtures/06-impossible-criterion`, run 2026-08-20

New fixture, built during this milestone. `split_odd(target)` must return two
primes summing to 7, 9, 11 and 13; `11` is impossible — every prime but `2` is
odd, two odd primes sum to an even number, so an odd target needs `target - 2`

### Decisions

- **Tier assignment inverted by human instruction, 2026-08-20: orchestrator
  `opus`, reviewer `sonnet`.** This reverses the decision recorded immediately
  below, which is retained rather than deleted because it states the risk that is
  now being carried differently.

  The concern raised and overridden: a weak reviewer does not fail loudly — it
  emits a confident, well-formatted per-criterion `PASS`, and the completion gate
  then opens on nothing. Moving the top tier to the orchestrator does not remove
  that risk; it relocates the guarantee onto the orchestrator's independent
  re-verification, which now runs first and at the higher tier. Two verification
  passes still stand between a worker's claim and a `DONE`.

  Propagated to: `agents/orchestrator.md` and `agents/reviewer.md` frontmatter,
  the `runtime-contract.md` tier and substitution tables, `fixtures/README.md`'s
  cross-reference, and `docs/implementation-plan.md` §39 (Amendment) and §40. Left
  deliberately unresolved at the time: whether `sonnet` can hold the reviewer
  role — an empirical question, with fixtures 01 and 03 as the tests for it.
  **Since settled: both run under the new pins, 13 / 13 PASS** (see Validation).

- **(Superseded) Orchestrator pinned to `sonnet`, reviewer to `opus` — the
  opposite of the initial proposal.** The first suggestion was to run the reviewer
  cheaper. That contradicts `runtime-contract.md`, which put the reviewer at the
  **Highest** tier and named it "the one to protect". The tier table already
  assigned orchestrator High and reviewer Highest; this pinned each role to the
  tier it was assigned instead of inventing a new mapping. The saving came from
  the orchestrator, which runs many turns per milestone.
- **Fixture 06 was retargeted after its first run, deliberately and on the
  record.** It was written to exercise the ladder; the orchestrator declined to
  delegate an impossible task, so it never did. The fixture now pins the behaviour
  it actually discriminates — impossibility proved, ladder deliberately not spent,
  pinned test intact, actionable escalation — and the ladder criterion is waived
  rather than reclassified as met.

  Rewriting a test to match its result is normally how a suite stops being worth
  anything, so the reasoning is stated in `EXPECTED.md` itself, in
  `fixtures/README.md`, and in `docs/implementation-plan.md` §40. It is defensible
  here only because refusing to burn five delegations on a provably impossible task
  is the right outcome whether or not a fixture asked for it — not because it is
  what happened. The original intent is recorded as unmet.

- **Worker escalation climbs tiers instead of repeating one, 2026-08-20 (by
  instruction).** The ladder was three fresh-context attempts, all at `haiku`,
  then the orchestrator. It is now: attempts 1-3 at `haiku`, attempts 4-5 at
  `sonnet` with an `Escalated: tier` packet note, then the orchestrator (`opus`).

  **Thresholds set by the human: 3 at Cheap, 2 at High.** An earlier draft
  escalated after 2 cheap failures to keep the total at 3 attempts; that was
  overridden in favour of the fuller ladder. Worker attempts before the
  orchestrator therefore rise from 3 to **5**. The cost is bounded — each attempt
  runs in a fresh context that never enters the orchestrator's, and the added
  rungs are below the orchestrator's own tier — but a task that exhausts the
  ladder now costs five delegations plus the orchestrator's pass before it
  reaches a human. Mitigated by an explicit early-exit rule rather than a lower
  cap: the orchestrator is told to stop climbing when two attempts fail for the
  *same* reason and that reason is requirement ambiguity, since more capability
  does not resolve ambiguity.

  Implemented as a **per-invocation model override on the same `worker` agent**,
  not a second agent definition: same instructions, same tool restrictions, same
  packet contract. `agents/worker.md` keeps `model: haiku`, so B5's acceptance
  evidence (which cites that exact line) is untouched. Editing that line instead
  would promote every delegated task to `sonnet` permanently — the precise cost
  the routing rule exists to avoid — so `runtime-contract.md` now says so
  explicitly.

  This adds required primitive **5** (per-invocation model override) to
  `docs/runtime-contract.md`. It is the only primitive with a clean degradation:
  a runtime without it skips attempts 4-5 and goes Cheap → orchestrator, losing
  two rungs and costing more, but nothing becomes unsound.

  Supersedes `.harness-dev/archive/post-B11-retry-escalate.md`, which recorded a
  3-attempt ladder at a single tier. That file is left unchanged — it is the
  record of what was verified then, not a description of current behaviour. Its
  validated behaviour — three fresh-context cheap-tier attempts, each informed by
  cumulative history, never reusing a failed context — survives intact as the
  first three rungs; what is new is what happens after them.

### Follow-ups

- **The ladder remains unexercised, by decision.** Attempts 4-5 and the early-exit
  rule have never run. `fixtures/06-impossible-criterion` was built to run them and
  could not: a task must be *delegable and still fail* to climb the ladder, and an
  impossible task is precisely the one a careful orchestrator keeps. Closing this
  properly needs a task beyond the Cheap tier but tractable at High — a capability
  gradient that would drift with every model release. Recorded as a waived
  criterion in `docs/implementation-plan.md` §40 and as a stated gap in
  `fixtures/README.md`, so it is not quietly rediscovered later. Revisit only if
  the ladder is observed misbehaving in real use.

- **Cost of a fully exhausted ladder.** Five delegations plus the orchestrator's
  own pass before a human sees it. Bounded, and each attempt is a fresh context,
  but worth measuring once the ladder has actually run rather than assuming.

- **Orchestrator early return, observed once under the `sonnet` pin.** Recorded in
  `.harness-dev/archive/B16.md`. The orchestrator is now `opus`, so the specific
  observation may no longer apply; if the symptom recurs at `opus` it is not a
  tier problem and should be diagnosed as something else.
