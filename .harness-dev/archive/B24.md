## B24 — Three worker tiers, reviewer matched to the work (post-V1)

Status: DONE

Specified in `docs/implementation-plan.md` §47, on the same branch as B23 (§46).
Both are recorded here; B23 is complete.

### B23 — route everything, tier by risk (§46)

B20 part 1 proposed removing `Write`/`Edit` from the orchestrator to make
delegation structural. **That was withdrawn before implementation, on three
findings:**

- The orchestrator must write `.harness/milestones.md` — that record *is* what
  the completion gate reads.
- A tool restriction is not enforcement while `Bash` is present, and the
  orchestrator needs `Bash` to re-run validation independently. This also
  corrects `docs/runtime-contract.md`, which claimed the reviewer "can only ever
  report findings" — it declares `Bash`, so that was overstated, and §43 leaned
  on the overstatement.
- **The measured 1:10 delegation ratio may have been the routing rule being
  obeyed, not ignored.** It tells the orchestrator to keep security-sensitive and
  cross-cutting work; the measured project is a policy engine and a sandbox seam.
  Reading it as non-compliance was an assumption.

The defect was never that the orchestrator *retained* work — it was that retained
work ran *in the coordinating context*, which is what compounds to 87%. So routing
stopped deciding **who** and started deciding **at what tier**: every task is
delegated, risk picks the tier, and risky work still gets maximum capability.

### B24 — three tiers and a derived review tier (§47)

Two defects that earlier sections introduced:

- **No middle tier.** §46 routed only to Cheap (`haiku`) or Top (`opus`). The
  reviewer ran at `sonnet` and no worker ever did, so ordinary implementation
  jumped to the most expensive model in the system.
- **The reviewer could be weaker than the work.** B16 pinned it to one tier, B17
  set that to `sonnet`, §46 then routed risky work to `opus` — leaving `sonnet`
  judging `opus` work, the exact failure `runtime-contract.md` names as the worst
  available here. **A fixed reviewer tier cannot be correct**, because the work's
  tier is chosen per task at routing time, long after the frontmatter is written.

### Decisions

- **No tool restriction, and the runtime contract corrected rather than quietly
  left.** Tool restriction removes the convenient path and makes the inconvenient
  one visible in the transcript. It is not an enforced guarantee while `Bash` is
  present. The guarantee that actually holds for the reviewer is structural: a
  fresh context that never sees implementation rationale.

- **The reviewer pairing is the part that does not degrade safely.** A runtime
  without per-invocation override loses ladder rungs — more expensive, not
  unsound. But it would review top-tier work at the reviewer's pinned tier, which
  is the weak-reviewer failure. On such a runtime, pin the reviewer to the top tier
  and accept the cost. Recorded in `runtime-contract.md` under primitive 5.

- **The bet §46 makes is stated in the agent file, not only the spec.** A worker
  gets a packet and a fresh read, not the orchestrator's accumulated understanding
  — which is exactly why retaining cross-cutting work was defensible before. The
  orchestrator is told to put the non-obvious constraint and the earlier decision
  into the packet, and that a task which cannot be expressed as one signals the
  milestone was cut wrong.

### Follow-ups

- **Whether the Mid tier is actually used is unmeasured.** Fixture 06 routes Cheap
