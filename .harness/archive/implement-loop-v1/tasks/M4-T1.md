TASK  M4-T1 — the loop counts DONE milestones per start (cap 10) and stops only on two failed steps in a row

Tier: Mid (sonnet). Routing: reason_code ORDINARY_IMPLEMENTATION — ordinary change to the driver's run loop with a clear test oracle.

Goal:
In the background driver (`scripts/implement-loop.py`, class `Driver`, method `run`, and `judge_step`),
(1) stop the loop once 10 milestones have reached DONE during this start, and
(2) stop on two consecutive failed steps instead of one; a single failed step followed by a step that makes progress keeps the loop running.

Relevant Requirements:
.harness/requirements.md FR6(b), FR6(d), AC4, Edge Cases ("A milestone SPLIT ... the cap counts DONE milestones only"; "A session ends with no change to state and no recognisable result: counts as a failed step").

Acceptance Criteria:
- M4-AC1 Driven through `start` by a fake session that completes a milestone per step, the loop stops after 10 milestones reach DONE during this start; milestones that were already DONE before the start, and milestones split into parts that are not yet DONE, do not count.
- M4-AC3 Two consecutive failed steps (crash, no recognisable result, no state progress, or the time limit) stop the loop; a single failed step followed by a step that makes progress does not.

Design (settled — implement exactly this):
- Add a module constant `MILESTONE_CAP = 10`.
- At driver start, before step 1, record the set of milestone ids whose status is already DONE in `.harness/state.json` (empty set if no state). After each step, "DONE this start" = ids whose status is DONE now and which are not in that initial set. Ids that disappear (a split milestone replaced by `M6a`, `M6b`...) simply are not DONE and do not count.
- Precedence after a step: anything `judge_step` returns other than PROGRESS (stopped by owner, time limit, finished, failed) is handled first; "finished: every milestone is DONE" wins over the cap when both are true. Only when the step made progress and DONE-this-start >= MILESTONE_CAP does the loop stop with outcome string exactly: `cap: 10 milestones reached DONE during this start` (build it from the constant).
- Failed steps: any outcome starting with `failed step` (no state progress, time limit; a crash with no state change already lands in "no state progress") is a failed step. Keep a consecutive-failure counter: a PROGRESS step resets it to 0; a failed step increments it. With 1 failure the loop runs another fresh step, logged as attempt 2 for the same milestone (`step N started: milestone Mx, attempt 2`). At 2 consecutive failures the loop stops with outcome `failed steps: two in a row; last: <the second failed step's outcome string>`. Log each step's own outcome line as now (`step N outcome: ...`).
- Remove the "interim for M2" comment on FAILED_STEP's return.
- Do not change the notification text, outcome.json shape, or any other stop condition — later tasks own those.
