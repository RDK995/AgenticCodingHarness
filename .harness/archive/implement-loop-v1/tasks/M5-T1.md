TASK  M5-T1 — ntfy sender is the default sink, reads its config at send time, never reveals the topic, never stops the loop

Tier: Top (opus). Routing: reason_code SECURITY — the ntfy topic is a private value; a leak through an exception string, a log line or stderr is expensive and easy to miss.

Goal:
Add an ntfy sender behind the existing notification seam in `scripts/implement-loop.py` (`file_sink` / `choose_sink` / `notify`, and `refuse` for the pre-start path) and make it the default sink. It reads the alert config file at send time, POSTs the message body to `<ntfy_server>/<ntfy_topic>`, and on any failure records "not sent" with a reason that never contains the topic, without stopping the loop.

Relevant Requirements:
.harness/requirements.md FR7, AC6, Constraints ("The ntfy topic is a secret: never stored in the repository and never printed"), Edge Cases ("Notification send fails ... the loop continues; the failure is recorded in the loop log"), FR13.

Acceptance Criteria:
- M5-AC1 A loop run through `start` and `stop` with the alert config path pointed at a test config sends its stop notification through the ntfy sender, which reads the config at send time and POSTs the body to `<ntfy_server>/<ntfy_topic>` on a local stub; no test touches the external network (AC6, FR7).
- M5-AC2 The topic never appears in stdout, stderr, `loop.log`, `commands.log`, `outcome.json`, or any error or exception text, including when the POST fails (AC6, FR7).
- M5-AC3 A missing or invalid config, a network failure, or an HTTP error status is recorded in `loop.log` as "not sent" with a reason, and the loop keeps running (AC6, Edge Cases).

Design (settled — implement exactly this):
- Config file shape: `{"ntfy_server": "https://...", "ntfy_topic": "<private>"}`. Default path `~/.config/harness-e2e/alert.json`.
- Path selection: new `start` option `--alert-config PATH`; when omitted, use env `HARNESS_LOOP_ALERT_CONFIG` if set, else the default path. Resolve it (expanduser) at `start` and persist only the PATH in `.harness/loop/config.json` (key `alert_config`). Never persist or log the topic or the file's contents. The driver reads the file afresh on every send (no caching).
- Sink choice: `--notify-file` given -> file sink (unchanged; existing tests rely on it). Otherwise -> ntfy sink using the persisted `alert_config` path. `refuse()` (start refused before the driver exists) uses the same choice, with the path resolved the same way.
- Valid config: a JSON object whose `ntfy_server` is a string starting `http://` or `https://` and whose `ntfy_topic` is a non-empty string with no `/`, whitespace, `?` or `#`. Anything else (file missing, unreadable, not JSON, wrong shape) is a failure with a plain reason such as `alert config missing`, `alert config is not valid JSON`, `alert config has no valid ntfy_server`, `alert config has no valid ntfy_topic`.
- Send: `urllib.request` POST of the UTF-8 message body to `ntfy_server.rstrip("/") + "/" + ntfy_topic`, timeout 10 s. The sink takes an injectable `opener` (default `urllib.request.urlopen`) so unit tests can avoid sockets. A 2xx response is sent; return the location string `ntfy HTTP <status>` (no server, no topic). Any non-2xx, `HTTPError`, `URLError`, timeout, `OSError` or other exception is a failure with a reason like `HTTP 403` or `network error: <exception class name>` — build reasons from status codes and class names, never from `str(exception)` or the URL. As a final guard, remove the topic from any reason string before it leaves the sink.
- Failure signalling: the sink raises one dedicated exception type carrying only the sanitized reason, raised `from None` so no chained exception carries the URL. `notify` catches every `Exception` from any sink (not only `OSError`) and logs `notification not sent: <reason>: <message>`; success logs `notification sent (<where>): <message>` as today. `refuse()` prints `notification not sent: <reason>` to stderr the same way.
- The message body never contains the topic; do not add the server or topic to any log line, outcome.json, stdout or stderr.
- Add help text for `--alert-config`. If `skills/implement-loop/SKILL.md` documents start options, add one line for `--alert-config`; otherwise leave it.

Test isolation (mandatory — the owner's real config exists on this Mac and must never be read by tests):
- In `.harness-dev/test-implement-loop.py`, `run_loop` must set `HARNESS_LOOP_ALERT_CONFIG` to a path inside the test's temp dir for every subprocess (nonexistent unless the test writes a config there), so tests that omit `--notify-file` exercise "config missing" instead of the real file. In-process unit tests of the sink use an injected opener or a temp config. No test may open a socket to anything but 127.0.0.1.

New tests required (Red first):
1. Through `start` then `stop` (AC1): run a stub HTTP server on 127.0.0.1 (stdlib `http.server`, ephemeral port, in a thread) recording each request's path and body; write a temp config pointing at `http://127.0.0.1:<port>` with a distinctive random topic; run `start` with `--alert-config <path>` and no `--notify-file`, then `stop`. Assert exactly one POST arrived, its path is `/<topic>`, its body is the stop message, and `loop.log` has `notification sent (ntfy HTTP 200)`. Prove send-time reading: after `start` and before `stop`, rewrite the config to a second topic and assert the POST used the new one.
2. Secrecy (AC2): with the distinctive topic, cover a successful send, an HTTP error status (stub returns e.g. 500 or 403) and a network failure (a 127.0.0.1 port with nothing listening). For each, assert the topic string appears in none of: start/stop/status stdout and stderr, `loop.log`, `commands.log`, `outcome.json`, `config.json`. Add an in-process test that, when the injected opener raises an exception whose message includes the full URL, the sink's raised exception's `str()`, `repr()`, its `__cause__`/`__context__` chain and the logged reason do not contain the topic.
3. Failure keeps running (AC3): for missing config, invalid JSON, wrong shape (no topic / non-http server), network failure and HTTP error status, `loop.log` records `notification not sent: <reason>` with a non-empty reason and the driver still completes normally (writes `outcome.json`, removes its pid file); a refused `start` still prints its reason and exits 1. At least one case must show the loop continuing past a failed send to a later step or to its normal finish.
