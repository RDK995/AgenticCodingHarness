TASK  M4-T3 — every stop writes a full outcome record and one plain-words stop message

Tier: Mid (sonnet). Routing: reason_code ORDINARY_IMPLEMENTATION — message and record shape settled below; clear oracle through `start`/`stop`.

Goal:
Whatever ends the driver (`scripts/implement-loop.py`, `Driver.finish`), it writes `.harness/loop/outcome.json` with the stop condition, milestone, branch and the owner's ask, and sends exactly one short plain-words stop notification naming which condition occurred, the milestone and branch it stopped on, and what the owner is asked to decide or do.

Relevant Requirements:
.harness/requirements.md FR6 (every stop writes an outcome record and sends exactly one stop notification), FR6(f) owner's stop, FR6(g) unexpected driver error, FR10, FR13.

Acceptance Criteria:
- M4-AC5 Every stop — including the owner's `stop` and an unexpected driver error — writes `.harness/loop/outcome.json` and sends exactly one stop notification naming which condition occurred, the milestone and branch it stopped on, and what the owner is asked to decide or do, if anything.

Current outcome strings produced by the driver (from earlier tasks; read the code to confirm):
`finished: every milestone is DONE`; `cap: 10 milestones reached DONE during this start`; `failed steps: two in a row; last: ...`; `stopped for the human: ...`; `signed out of Claude`; `usage limit reached[ (resets ...)]`; `stopped by owner`; `driver error: ...`.

Design (settled — implement exactly this):
- Map every outcome to a `condition` code: `finished`, `cap`, `failed_steps`, `human_stop`, `signed_out`, `usage_limit`, `owner_stop`, `driver_error`. Do the mapping in one function (a prefix match on the outcome string, or by having the run loop carry the code — your choice; keep it simple). An unmapped outcome maps to `driver_error`.
- outcome.json keys: `outcome` (the existing string, unchanged), `condition`, `time`, `milestone`, `branch`, `ask`. Keep `outcome`/`time`/`milestone` as they are today so existing tests hold.
- `milestone`: the milestone the last step worked on (`self.milestone`); if none ran, `current_milestone(project)`; if still none, `none`.
- `branch`: `git rev-parse --abbrev-ref HEAD` in the project, via the existing `git_output` helper, read at finish time; `unknown` if unavailable.
- `ask` per condition (plain words, no jargon):
  - finished: `Nothing to do: every milestone is done. Review the branch when you are ready.`
  - cap: `Check the work so far, then run start again to carry on.`
  - failed_steps: `Look at .harness/loop/loop.log and the last step's output, then run start again.`
  - human_stop: `Read <milestone>'s entry in .harness/milestones.md and decide what happens next.` — and when the outcome carries the session's own sentence (text after `stopped for the human: `), use that sentence as the ask instead.
  - signed_out: `Sign in to Claude again (run claude, then /login), then run start again.`
  - usage_limit: `Wait for the usage limit to reset<, at TIME if known>, then run start again.`
  - owner_stop: `Nothing: you stopped it. Run start again to carry on.`
  - driver_error: `Look at .harness/loop/loop.log: the loop hit an unexpected error.`
- Notification body (one message, short): `implement loop stopped: <outcome>. Stopped on milestone <milestone>, branch <branch>. <ask>`
- Exactly one notification per stop stays guaranteed (the existing `self.notified` guard); if building the record or message itself fails, still write what you can and still send one notification — the driver must always end with its notification.
