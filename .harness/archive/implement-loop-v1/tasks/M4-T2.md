TASK  M4-T2 — the loop stops at once for a human stop, a sign-out, or an exhausted usage limit

Tier: Mid (sonnet). Routing: reason_code ORDINARY_IMPLEMENTATION — detection rules are settled below; clear test oracle through `start`.

Goal:
After each step, the driver (`scripts/implement-loop.py`) recognises (a) a session that stopped for the human and (b) a session whose output says Claude is signed out or the plan's usage limit is reached, and stops the loop immediately — no further session — with a distinct outcome.

Relevant Requirements:
.harness/requirements.md FR5 (driver reads state, "not the session's own claims alone"), FR6(c), FR6(e), AC4, Edge Cases (first session plans milestones; a planning STOP is an FR6(c) stop).

Acceptance Criteria:
- M4-AC2 A session that stops for the human — a milestone BLOCKED, an escalation, a decision needed, an exhausted continuation/retry/review-cycle cap, a planning stop (including the first session when `milestones.md` does not yet exist), or any other STOP that is not a normal phase boundary — stops the loop without another session.
- M4-AC4 Session output reporting that Claude is signed out or that the plan's usage limit is reached stops the loop at once with no second session, and the stop message includes the reset time when the output gives one.

Design (settled — implement exactly this):
1. Result marker. The step session cannot change `/harness:implement`, so the driver asks for a result line through the session command, not the prompt: in `session_command`, add `--append-system-prompt` with a module constant `RESULT_INSTRUCTION` reading:
   "When you finish, end your final message with exactly one line: `HARNESS_LOOP_RESULT: BOUNDARY` if you stopped at a normal milestone or phase boundary (for example a milestone set to REVIEW, DONE or SPLIT, or a phase handed off), or `HARNESS_LOOP_RESULT: HUMAN — <one plain sentence saying what the owner must decide or do>` if you stopped for the human for any other reason (a milestone BLOCKED, an escalation, a decision needed, an exhausted continuation, retry or review-cycle cap, a planning stop, or anything else)."
   The prompt argument stays exactly `/harness:implement`. The check session shares `session_command`, so it carries the same flag; that is intended ("built exactly like every step session"). Existing command-line/permission tests must keep passing; extend them to assert the new flag is present, do not loosen them. The instruction text is not secret; the command log still shows the prompt by length only, as today.
2. Read the step's output: the whole `.harness/loop/step-<N>.out` for this step.
3. Account stops (checked first, before state; never counted as a failed step, never retried):
   - Signed out — case-insensitive match of any of: `not logged in`, `please run /login`, `invalid api key`, `oauth token has expired`, `authentication_error`. Outcome string: `signed out of Claude`.
   - Usage limit — case-insensitive match of any of: `usage limit`, `hit your limit`, `limit reached`. Outcome string: `usage limit reached` plus, when a reset time is found, ` (resets <time>)`. Reset time: text after `resets` / `reset at` up to end of line or a `·`/`|` separator, trimmed; or a `|<unix epoch seconds>` suffix (e.g. `Claude AI usage limit reached|1762531200`) rendered as local time `%Y-%m-%d %H:%M %Z`. No reset time found → no parenthesis.
4. Human stops (after account stops):
   - Any milestone in `.harness/state.json` has status `BLOCKED` after the step → outcome `stopped for the human: milestone <id> is BLOCKED`.
   - Planning stop: `.harness/milestones.md` did not exist before the step and exists after it → outcome `stopped for the human: milestones planned; review the plan`.
   - Otherwise, the LAST line in the output that starts with `HARNESS_LOOP_RESULT:` says `HUMAN` → outcome `stopped for the human: <the sentence after the dash>` (or `stopped for the human` if it gave none).
   A BOUNDARY marker never by itself counts as progress: state still decides progress (state unchanged + BOUNDARY = failed step, as today).
5. Precedence in the step judgement: stopped by owner > account stops (signed out / usage limit) > time limit > every milestone DONE (finished) > human stops > progress / failed step. The 10-milestone cap and two-failed-steps logic in `Driver.run` (task M4-T1, already committed) stay as they are and only see PROGRESS / `failed step...` outcomes; the new outcomes stop the loop at once.
6. Do not change notification wording, outcome.json shape, or the cap/failure counting — another task owns the stop message.
