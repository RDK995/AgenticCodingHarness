### The fixture

A link shortener whose five components divide honestly by tier — HTTP API, Link
Service, Store, Clock, Config. That division is not a strawman; it is how the
responsibilities split. It is also exactly the shape that invites a build order of
config → clock → store → service → API, in which nothing is demonstrable until the
last milestone.

**The trap is symmetrical: 5 components and 5 acceptance criteria.** A layered plan
and a sliced plan can both produce five milestones, so count discriminates nothing.
What separates them is countable from the `### Architecture` fields:

- every milestone names >= 2 components (a slice crosses boundaries; a layer sits inside one)
- no milestone names exactly one component — the layered signature
- C1 and C2 recur in >= 3 milestones, since every behaviour is served through the
  API and decided by the service

None of those depend on the domain, which is the property that makes the fixture
useful on another project.

### Validation — baseline, before any gate change

```
M1 — A posted URL can be followed through the API and survives restart   5   C1,C2,C3,C4,C5
M2 — A custom alias can be claimed, and only once                        4   C1,C2,C3
M3 — A link stops redirecting once it expires                            4   C1,C2,C3
M4 — Followed links are counted and reported by the stats endpoint       5   C1,C2,C3
```

5 / 5 mechanical checks PASS. M1 is a walking skeleton; every milestone crosses at
least two components; C1 and C2 appear in all four; all five components covered;
every milestone carries an HTTP entry-point criterion.

Criteria are single assertions about observable behaviour — `302` with a `Location`
header, `400` and creates no link, `410` with no `Location`, and expiry evaluated at
read time with the row still present. None carries a subsystem. It also declined the
fixture's central trap, folding restart-survival into the skeleton rather than
turning five acceptance criteria into five milestones.

### Decisions

- **The gates were withdrawn on the fixture's own evidence.** §45 proposed a
  demonstrability gate testing the assertion rather than the driver, plus a
  one-assertion-per-criterion rule. Both were argued from three weak slices seen on
  a real project — and those came from **re-cutting existing component milestones**,
  a different and harder task than planning from scratch. The weakness does not
  reproduce in generation. Adding a gate would have meant a permanent per-turn cost,
  in the file §42 measured, for a failure with no reproduction.

  This is the second change this session killed by measuring first; §42's batching
  instruction was the first. Building the fixture before the gates is what made it
  visible.

- **The fixture is the part that generalises.** It locks in current planning
  behaviour, its discriminators are domain-independent, and it catches a regression
  under a future model or prompt change. That was the actual request — confidence
  the harness plans well on *another* project — and a gate would not have provided
  it.

- **No examples were added.** §44 already demotes the layered example to `Bad` and
  the baseline passes without further prose.

### Follow-ups

- **Weak slices on re-cuts, under-specified.** Three of sixteen re-cut milestones on
  a real project drove a real entry point while asserting internal structure, and one
  criterion carried a whole subsystem. Reproducible only on re-cuts, not on
  generation. If it recurs, the right response is a re-cut-specific fixture, not a
  gate on generation.
- **Ordering by integration risk is stated and unchecked.** Fixture 07 does not test
  it; its four slices have no strongly risk-ordered arrangement to discriminate.
