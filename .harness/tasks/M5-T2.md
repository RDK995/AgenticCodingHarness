TASK  M5-T2 — every message names its project, and an over-long body is cut to ntfy's 4096-byte limit with a visible marker

Tier: Cheap (haiku). Routing: reason_code BOUNDED_LOW_RISK — one small isolated function at the notification seam with stated input and output.

Goal:
In `scripts/implement-loop.py`, every notification body — from `notify` (driver) and from `refuse` (refused start), whichever sink is used (file or ntfy) — is labelled with the project it comes from and fits ntfy's 4096-byte limit.

Relevant Requirements:
.harness/requirements.md FR7 ("Every message names the project it comes from"), AC5 ("messages over ntfy's size limit are truncated with a visible marker"), Constraints ("ntfy message bodies stay within ntfy's ~4096-byte limit").

Acceptance Criteria:
- M5-AC4 Every message names the project it comes from, and a body over ntfy's 4096-byte limit is truncated to fit with a visible truncation marker (AC5, FR7).

Design (settled — implement exactly this):
- Add one function, e.g. `prepare_message(project: Path, message: str) -> str`, and call it in both `notify` and `refuse` before handing the text to any sink. The text it returns is what is sent AND what is written to loop.log / stderr.
- Label: prefix `[<project directory name>] ` (i.e. `f"[{project.name}] {message}"`).
- Limit: constant `NTFY_LIMIT = 4096` (bytes, UTF-8). If the labelled text encodes to more than 4096 bytes, keep the longest prefix such that prefix + marker encodes to at most 4096 bytes, cutting only at a character boundary (never split a multi-byte character), and append the marker ` … [truncated]`. Text at or under the limit is unchanged apart from the label.
- `refuse` currently takes no project label input — pass the project into it (`command_start` has it).
- Do not change any other wording.

New tests required (Red first), in `.harness-dev/test-implement-loop.py`:

2. A refused `start` (e.g. the project on main, or open questions — reuse an existing refusal arrangement): the one notification contains the project label.
3. Unit tests of the function (load the module the way existing unit tests in the file do): a short message is returned labelled and otherwise unchanged; a message of, say, 10000 ASCII characters returns text whose UTF-8 encoding is <= 4096 bytes and which ends with `[truncated]`; a long message made of multi-byte characters (e.g. `"é" * 5000` or an emoji) also fits, ends with the marker, and decodes cleanly (no split character); a labelled message of exactly 4096 bytes is not truncated.
Update any existing assertion that compared exact notification text so it accounts for the label, keeping what it checked.
